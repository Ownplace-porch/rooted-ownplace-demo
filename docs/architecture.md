# Architecture

The protocol is the center of Rooted. A creator bot creates `kinfolk.json` and `story.json`, then creates a manifest containing the SHA-256 hash of each canonical JSON object. Current packages sign the manifest with an Ed25519 Kinfolk identity; the signature envelope references the manifest hash. Posts are encrypted by default (M16 #116, below); public posts and the older paid-gating packages are not. Timeline reads authenticate every history package (manifest/signature/content hashes) before display: `timeline.json` is an untrusted cache hint, and display metadata derives solely from verified `timeline/<id>/` packages. Legacy `demo-placeholder` envelopes are rejected, never displayed as authenticated. Followed local porches (M10): a timeline read also pulls each contact with a `local:` address under the stores root (the path must stay inside that root; an escaping symlink is skipped). Each porch is verified on its own, so a tampered package is excluded without failing the rest. Entries carry an origin tag.

Remote porches (M11 #90): an `https:` contact is the base URL of another porch, and the follower reads it through the read-only `HttpsPorchStore`. With no directory listing over plain GET, the porch's `timeline.json` only names which story ids to try (at most 50, unsafe ids dropped). Every package still passes the same Ed25519 manifest/signature/hash verification before display, and unsigned index fields are never shown. Requests are GET only, with a 5 s timeout, a 1 MB cap per object and no redirects. Hosts that are localhost, single-label, IPv6 literals, or loopback/private/link-local/CGNAT IPv4 literals are refused before any fetch (a lexical check; contacts are operator-written). A remote porch that is down, malformed or oversized is reported as `porch unreadable` and loses only its own entries. The publishing side exposes its porch at `GET /porch/<backend>/timeline.json` and `GET /porch/<backend>/timeline/<id>/<file>`, which serves only package files (`kinfolk.json`, `story.json`, `manifest.json`, `signature.json`, `entitlements.json`). `contacts.json` and everything else return 404. Sealed bodies stay sealed. Remote public keys are still self-asserted: pinning a followed porch's key is a separate identity decision.

Two Kinfolk, one cloud each (M15 #100): the two local folders are two different Kinfolk, not two copies of one. `demo/stores/nextcloud-sim` is Alex's porch (`kinfolk-alex`) and `demo/stores/google-drive-sim` is Sam's (`kinfolk-sam`), each with its own Ed25519 key. The mapping lives in one place, `DEMO_KINFOLK` in `@rooted/timeline`. A post is written through the `ObjectStore` interface to its author's porch only, and to that porch's real cloud only when it is enabled: Alex to the kevcloud Nextcloud (`KEVCLOUD_*`), Sam to Google Drive (`GOOGLE_DRIVE_SYNC=1`). Nothing is mirrored between porches. `npm run publish` seeds one signed story per Kinfolk and writes each porch's `contacts.json` to follow the other at a `local:` address, pinned to the other's key fingerprint. Each column in the web page is one porch: its owner's posts plus the porches that owner follows, read from that porch's own address book. The web write token belongs to one operator Kinfolk (Alex): the composer posts only as Alex, and the contacts panel edits Alex's address book. The `npm run post` CLI refuses author ids that have no porch. Per copy (M15 #111), `OWNPLACE_OPERATOR_ID`, `OWNPLACE_OPERATOR_NAME` and `OWNPLACE_OPERATOR_BIO` replace the operator's id, name and bio in `DEMO_KINFOLK`, keeping the operator's porch and cloud. They are validated once at load (safe Kinfolk id, not Sam's; name 1 to 120 characters after trimming; bio at most 500), and the server and every CLI refuse to start on invalid settings with a fixed message that never echoes the value.

Verification is per porch (`npm run verify`), not cross-backend parity. For each porch: the latest package verifies and is signed as the porch owner; every `timeline/` history package verifies and is signed by the owner's key; the porch follows the other demo Kinfolk at their `local:` porch, pinned to that Kinfolk's key; and the followed entries verify against that key. The two porches must hold different keys. `npm run parity` compares each real cloud only with the porch it maps to.

OwnPlace reads the two folders through Vite's static demo directory and renders them as separate simulated backends. In a deployed app, the browser/client would use a configured adapter or a local sync layer rather than trusting a public static directory.

`WebDavStore` and `GoogleDriveStore` are intentionally scaffolds. They fail loudly until a real, user-authorized implementation is supplied. This prevents the demo from implying that local folders are cloud integrations.

Invitations (M12 #92): a creator is named by the lowercase hex SHA-256 of their Ed25519 public key (SPKI DER). The fingerprint stays stable when storage moves and reveals no location. `GET /i/<fp>` is a public landing page, and `GET /i/<fp>.json` is the invite document: fingerprint, display name, bio, and a porch path relative to the invite (`../porch/<backend>`). Following by invite (`POST /api/contacts/invite`, operator only) trusts nothing in that document:
- The link must be https and pass the remote-porch host checks.
- The porch must be same-origin with the invite.
- The follow succeeds only if the porch holds a verified package whose signer's key fingerprint equals the link's. The contact's display name comes from that signed package.

The contact is stored as `op-<first 12 hex>` with its `fingerprint`, so a later slice can enforce the pinned key on every read and survive a storage move.

Which porch an invite names (M14 #97, revised in M15 #100): `GET /i/<fp>.json` checks `nextcloud-sim`, then `google-drive-sim`, and names the porch whose signed identity has that fingerprint, so each Kinfolk's own invite link resolves to their own porch. The **Your invite** panel's `GET /api/invite` (no `backend` parameter) reads only the operator's porch and returns 404 until the operator has posted. #97 let it fall back to the other folder, which assumed both folders held one person; with two Kinfolk that fallback would hand the operator someone else's invite. `GET /api/invite?backend=<name>` still reads only that backend (400 unknown, 404 no identity).

Pinned identity and porch moves (M13 #94): a contact followed by invite keeps its `fingerprint` and `invite` link.
- **Pinning:** on every read, and on story open, that porch only contributes packages whose signer key matches the pin. Anything else is skipped as `signer does not match followed creator`, and it still owns its id so nothing can fall through.
- **Moves:** if the pinned porch is unreadable, or serves nothing signed by the pinned key, the follower re-resolves the stored invite under the M12 rules. If the invite now names a different porch with a post by the same key, that porch is used and the saved address is updated. The contact id, pin and invite stay the same, so there is no second follow and no duplicate.
- **Limits:** this covers moves behind the same OwnPlace host. Moving to a new domain needs a creator-signed move notice (future).


Wall posts and comments (M15 #101): a **wall post** is a post pointed at a Kinfolk, `to: { fingerprint }`. A **comment** is a post pointed at a post, `inReplyTo: { fingerprint, storyId }`. Each is an ordinary Ed25519-signed story package on its **author's own porch**, and the target is a signed `story.json` field. Nothing is written to anyone else's storage. A package with a malformed target, or with both fields, fails verification (`malformed reply target`).
- **How readers attach them:** a timeline read (`readThreadedTimeline`, used by `GET /api/timeline`) merges the reader's own porch and every porch it follows, as before. Replies then attach to their targets instead of showing as plain posts. The porch **owner** is the one key that signed every verified post on the reader's own porch; the response names it as `owner`. If there is no single signer, there is no owner and no wall posts are shown.
- **Wall posts** show only on the column whose owner they name, labeled "Sam → Alex's wall".
- **Comments** show under the top-level entry whose signer fingerprint and id they name, oldest first. A comment whose target is not in the read is dropped. Comments on comments are not threaded.
- **Who sees them:** readers see replies only from porches they follow, and a pinned contact's signer rule (M13) applies, so a reply signed by any other key is skipped.
- **Sealed posts:** sealing replies to a Kinfolk-only post's readers is **not in this slice**. The writer can't learn those readers' keys. Replies are always public: signing one with sealed readers is refused, commenting on a sealed post is refused, and a reader never attaches a reply to a sealed post or shows a sealed reply.
- **Writing:** `POST /api/post` accepts `{ body, inReplyTo }` or `{ body, to }` from the operator. Before signing, a comment must name a post in the operator's own threaded view, and a wall post must name the pinned key of a Kinfolk the operator follows. The CLI takes `--reply-to STORY_ID` or `--wall CONTACT_ID` and applies the same checks.
- **Deleting:** an author deletes their own comment or wall post from their own porch (`DELETE /api/post?id=` or `npm run delete-reply`) and from that porch's cloud. Readers stop showing it on their next read. The flat latest copy is repointed at the newest remaining package so the deleted words don't linger there. Plain posts can't be deleted in this slice.
- **Hiding:** the target can hide someone else's reply aimed at them (`POST /api/hidden`). The hide list is `hidden.json` on the reader's own porch. It is private (never served under `/porch/`) and changes nothing on the author's porch.

Encrypted by default (M16 #116, slice 1 of #115): a porch folder is readable by anyone with the link, so encryption is the only lock. Crypto is demo-grade (Node primitives, not audited).
- **Epoch key:** each author has one random 256-bit epoch key in their identity dir (`<id>.epoch.json`, never published). A post's title, body, `createdAt`, media and `to` / `inReplyTo` are sealed with it (AES-256-GCM; the author id and story id are associated data). The signed `story.json` then holds only `{ id, authorId, encrypted }`. A package with any other clear field beside `encrypted` fails verification. The Ed25519 signature covers the ciphertext, so a tampered ciphertext is rejected before any decryption.
- **Readers:** the epoch key is wrapped to the author and every **mutual follow**: a pinned contact whose own porch pins the author back. Each reader's X25519 key comes from the signed `kinfolk.json` (`encryptionKey`) of a package on their porch that verifies against the pin. Only `local:` porches can show a follow-back (`contacts.json` is never served), so `https:` follows wait for slice 2's follow requests. Mutual follows are auto-accepted in this slice.
- **Wrap file:** `keys.json` at the porch root, served under `/porch/<backend>/keys.json`. Each wrap is `{ ephemeralPublicKey, keyNonce, wrappedKey }` (same per-wrap ephemeral X25519 construction as sealed bodies). It names no reader: no id, fingerprint or public key. Readers trial-decrypt every wrap, and wraps are shuffled. The count of wraps does show how many readers there are. `keys.json` is unsigned: a swapped wrap can only yield a key that fails the GCM check on signed ciphertext, so it fails closed. Every post re-wraps the current epoch to the current mutual set, so a new mutual can read the whole epoch (#115 Q1). `npm run publish` re-wraps once both demo Kinfolk have posted, since the first to post could not yet see the other's key.
- **Reading:** a read takes the reader's X25519 private key (`FollowOptions.readerKey`). Without a wrap for it, an encrypted post is left out and reported once as the fixed skip reason `encrypted post`, with nothing about its title, date or size. Signature checks, pinning and invite resolution work without any key. The web API opens encrypted posts only for an authenticated request (or local dev mode without a token), reading each column as its porch owner with that owner's key from this machine. Anyone else gets the stranger's view.
- **Metadata:** new story ids are `story-<32 random hex>`, with no date or title. `timeline.json` is an unsigned hint: public posts keep their clear fields, encrypted posts are bare ids in id order, and the file no longer carries `updatedAt`. Older plaintext packages (dated ids included) stay readable.
- **Public opt-in:** `npm run post -- --public` or the composer's **Public post** box writes today's signed plaintext format. Paid-gating flags keep the sealed-body format and cannot be combined with `--public`.
- **Not yet:** a new epoch on removal and follow requests (slice 2); an encrypted index, Drive file-id index and redirect allowance (slice 3). Host metadata (file names, sizes and dates from a share listing) and size padding are not addressed. The porch folder still holds `contacts.json`, `subscribers.json` and `hidden.json`, which a cloud sync of the whole folder (Drive `rclone copy`) exposes to anyone with the link; `/porch/` never serves them.
